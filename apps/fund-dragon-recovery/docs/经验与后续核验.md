# 经验与后续核验

## 已确认的坑

1. `基金收益−创业板收益` 会隐含市场暴露为1。现金和其他持仓造成的残差可能压成目标负系数；负值不能解释为清仓。
2. 等权双龙而不控制两股差异，会把持仓比例差误写为总仓位变动。应分离合计敏感度与两股差异。
3. β/季报权重不是“回补百分比”。历史峰值与已披露中位权重相似，也不是独立验证。
4. 后20条净值不一定是后20个交易日。未更新、跨日、缺收益、分红必须分别处理。
5. 单位净值跌、公布收益不跌可能是分红。不能一律当作来源错误或卖出。
6. 前十大未出现不是0；不同报告期不能拼成一个“当前持仓”；持仓权重的分母必须核对组合总净资产。
7. 不应按名称排除科创/创业板主动产品，或用高权重门槛删掉减仓/潜在回补样本。
8. 基金净值上涨不代表规模同步增长，申赎未知时不能粗估当前持仓金额；份额类净资产不等于份额数量。
9. 同一产业链其他个股可能制造“双龙回补”假象；个基其他重仓股对照能降级一部分候选，也可能因数据不足而无法区分。
10. 原始响应哈希必须在发布时复核。补抓不能覆盖复制来的同名文件；每个批次需要独立路径。
11. Windows Git 会归一化文本换行。发布文件与Git/HTTP哈希统一按LF计算；不要用HTML字节数或出现某几个字符串来代替数据验收。
12. 没有调度证据就不能在页面承诺“08:40自动更新”。本项目目前明确为手动更新。
13. 生产校验应可见、分项并有超时。Windows下本轮在长流程内校验出现等待，独立进程逐项核对通过58项；已把发布后的验收改为独立进程并限制总等待时间，没有据此断言根因。等待结果不明时，先查线上构建和远端提交，再单独复核，不重复发布。相同数据构建号也可能对应文档/流程修订，必须同时核对完整发布清单。

## 每次更新要看

- 业务日是否是最新已完成交易日，主数据采集时间是否足够新；晚到净值应重跑新批次。
- 同日覆盖、净值错误、固定宽窄篮子覆盖和个基对照缺行情名单；数据不足是否仍误生成当前信号。
- 较强和初步候选的来源、个基对照是否完整；区分“统计不支持”和“资料不足”。
- 新季度是否仍在滚动披露；接口分页完整只表示返回目录翻完，不保证全市场或全部报告已发布。
- 页面、JSON、CSV、配置、源码、验收和Git/生产构建是否同一版本；主域名别名是否实际切到新数据。

## 后续迭代次序

先扩大管理人原报与份额关系的核验样本；增加不同规模、集中度、策略、含现金/转债和分红类型，核验供应商字段语义。

再建立真正向前的观察档案：每个业务日保留当时可见样本、候选等级、下一期原报结果和误判原因。后续披露仍是滞后的期末真值；对区间内交易不能凭期末差直接下结论。未披露新建仓的全市场发现池是当前漏报来源，扩池需先验证数据与误报成本，不能靠降低所有门槛来弥补。

最后在独立时段与留出基金上评估阈值、遗漏因子、事件窗口和周转假设。对误判按现金暴露、同行持仓、个股差异、共线、旧持仓、来源修订分组复盘。保留全部弱迹象，但只把足够强且经交叉核查的候选提升优先级。仍不把收益敏感度直接标成实时仓位。

暂不启用定时任务。后续确需调度时再明确运行环境、交易日规则、晚到数据复核和失败提醒，并先验证一段手动流程记录。
