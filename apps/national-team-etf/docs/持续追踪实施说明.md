## 2. 实际数据源与延迟

| 数据源 | 用途 | 频率 | 实测延迟 / 限制 |
| --- | --- | --- | --- |
| `qt.gtimg.cn` 批量快照（GBK） | 盘中价格、涨跌幅、成交额、换手率、折溢价/IOPV、行情时间 | 连续竞价 60 秒；其余 300 秒 | 快照自带行情时间；`stale_seconds=180`，超时一律标 `stale` 并降为 L0，不解释为「没有托底」 |
| 同页 JSONP（`qt.gtimg.cn`） | 浏览器端实时行情，避免每分钟 Git 提交 | 60 秒 | 直连供应商，受浏览器与供应商可用性影响；页面在能力不足时静态降级 |
| 上交所 ETF 基本信息清算后份额 | 正式份额 | 盘后/次晨 | `TOT_VOL` 万份；接口最近 10 个交易日；按业务日记账 |
| 深交所 `scsj_fund_jjgm` | 正式份额 | 盘后/次晨 | 接口明示 T 日晚间值仅供参考、以 T+1 早间为准；页面标「待次晨复核」 |
| 本地分钟画像 `profiles/*.json` | 历史同一时段成交额基线 | 每轮归档 | 需累计 `min_days=5` 个完整交易日；不足时 `cold_start=true`，只出 L1 线索 |
| 东财 `push2his trends2` | 可选分时补充 | 未启用 | 实测连续 `RemoteDisconnected`，**不作为基线必需来源**，不伪造历史 |

**不宣称覆盖全市场**：核心 15 只固定；扩展池来自 `config/registry.json` 中 `watch` 的境内股票 ETF；供应商目录分页完整也不等于交易所全市场覆盖，新上市或未收录 ETF 可能遗漏。页面明确标注该说明。

**字段映射**（腾讯 88 字段快照）：`f[3]` 价格、`f[30]` 行情时间、`f[32]` 涨跌幅、`f[37]` 成交额(万元)、`f[38]` 换手率、`f[77]` 折溢价、`f[78]` IOPV。指数必须沿用 `INDEX` 自带前缀（`sh000300`），不能经 `symbol()` 生成 `sz000300`。

**盘中不作份额反推**：快照换手率的分母可能是昨收份额，且 `bfq` 日线**最后一行**的换手率分母在 T 日也可能是昨收份额、T+1 才修订。盘中只用价格/成交/折溢价线索，正式份额一律等交易所披露。

## 3. 判断纪律（不可越过）

1. 核心 ETF 角色、放量、大单、折溢价、同步交易，都不能直接证明国家队身份。
2. 不输出未经校准的国家队概率，不编造国家队盘中买入金额；身份恒为 `I0 当日买卖主体未确认`。
3. 过期行情、日期错位、缺失、休市，一律标 `unavailable` / `out_of_session`，**不得解释为「没有国家队买入」**。
4. 二级市场买卖可能不改变总份额；盘后没有净申购，**不能单独判定**盘中承接信号错误。
5. 补采/回放的历史事件标 `replayed=true`，不冒充正在发生的新事件。
6. 冷启动（基线交易日 < 5）最多 L1，只输出线索，不升级。
7. 规则写在配置里，不因一次行情自动调整阈值；调整须记录误报、漏报与发现延迟的变化。
8. 只监控、提醒和更新页面，**不操作证券账户**。

## 5. 命令（启动 / 停止 / 补跑 / 回放）

所有命令在 `D:/work_code2/gjd_research` 下执行；先核对 `--help`，**示例中的日期不要复制**。

```powershell
# 盘中采集：单轮 / 常驻 / 限时试跑 / 计划任务模式
python -X utf8 intraday.py --once
python -X utf8 intraday.py --scheduled       # 计划任务用；非交易时段自动降频跳过
python -X utf8 intraday.py --loop
python -X utf8 intraday.py --loop --duration 180
python -X utf8 intraday.py --status
python -X utf8 intraday.py --watchdog          # 断线/崩溃自愈补跑一轮

# 通知队列（由 WorkBuddy 定时任务消费）
python -X utf8 intraday.py --notify-drain
python -X utf8 intraday.py --notify-drain --notify-ack

# 基线与回放
python -X utf8 intraday.py --baseline
python -X utf8 intraday.py --replay data/intraday/2026-11-13/snapshots.jsonl

# 盘后初值（不发布）；次晨复核（可发布）
python -X utf8 postclose.py --retries 3 --wait 20
python -X utf8 postclose.py --status
python -X utf8 morning_review.py --dry-run
python -X utf8 morning_review.py --verify-only
python -X utf8 morning_review.py

# 日频正式入口（次晨复核内部调用，不绕过发布闸门）
python -X utf8 update.py --phase close --end YYYY-MM-DD
python -X utf8 update.py --phase final --deploy
python -X utf8 update.py --offline --deploy

# 周报
python -X utf8 weekly_report.py --days 7

# 定时任务：查看 / 前置检查 / 安装 / 停止 / 卸载
python -X utf8 scheduler.py --list
python -X utf8 scheduler.py --check
python -X utf8 scheduler.py --install --dry-run
python -X utf8 scheduler.py --install
python -X utf8 scheduler.py --status
python -X utf8 scheduler.py --uninstall
```

**停止**：`scheduler.py --uninstall` 删除全部 `GJD_*` 计划任务并写 `active=false`；这是最干净的停止方式（不需要结束进程，因为采集不再是常驻）。若曾手动启动 `--loop`，先结束对应 `python.exe` 进程并确认 `data/intraday/intraday.lock` 已释放。遗留过期锁可用 `--force-lock`（必须先确认旧进程已退出）。

**补跑**：盘中历史用 `--replay`；盘后初值用 `postclose.py --end YYYY-MM-DD`；正式发布用 `update.py --offline --deploy`（用已留档且仍在时效内的原始批次重算）。补跑事件一律带来源与时间，不伪装成新事件。

## 6. 任务清单与时间（Asia/Shanghai）

本机时区实测 `UTC+08:00 / 中国标准时间 / 夏令时=False`，与 `Asia/Shanghai` 一致；`scheduler.py --check` 会拒绝在其它时区或启用夏令时的机器上安装。任务按本机时区运行，**迁移机器必须重新核对**。

| 任务名 | 触发 | 实际命令 |
| --- | --- | --- |
| `GJD_Intraday_Tick` | **每分钟**（`MINUTE /MO 1`） | `intraday.py --scheduled` |
| `GJD_Intraday_Watchdog` | 每 10 分钟 | `intraday.py --watchdog` |
| `GJD_PostClose_1630` | 每日 16:30 | `postclose.py --retries 3 --wait 20` |
| `GJD_PostClose_1900` | 每日 19:00 | 同上 |
| `GJD_PostClose_2130` | 每日 21:30 | 同上 |
| `GJD_Morning_1000` | **每日** 10:00（含周六） | `morning_review.py` |
| `GJD_Weekly_Report` | 每周一 09:00 | `weekly_report.py` |

- 盘后/次晨全部用 `DAILY`，**不按周一至周五过滤**，避免漏掉周六对周五业务日的次晨复核。
- 交易时段、午休、休市日、集合竞价由 `session_state()` 按 `config/intraday_rules.json` 处理：连续竞价 60 秒，集合竞价/午休/休市 300 秒；休市不刷新行情属正常，**不判采集故障**。
- **本机实测**：`schtasks /Create /SC ONLOGON` 返回「拒绝访问」（需要更高权限），而 `MINUTE` / `DAILY` / `WEEKLY` 均可创建。因此改成「系统每分钟唤醒 + `--scheduled` 脚本内节流」，不依赖登录时启动的常驻进程；重启、崩溃、断线后都能由调度器自愈，比常驻方案更稳。被节流的唤醒不写 Python 运行日志；启动器只留一行纯数字时间戳的轻量触发记录，避免刷屏与中文编码乱码。
- 休市日清单目前只有周末 + 配置里的 `holidays`，**未接入交易所交易日历**，不保证法定节假日完整（见 §10）。
- 计划任务只调用 `_scheduled_run.cmd`（纯 ASCII，由 `scheduler.py --install` 生成，含本机 Python 绝对路径）；仓库快照不同步这个启动器，恢复环境时重新运行 `--install`。

WorkBuddy 定时任务（通知消费）：见 §7。

## 7. 通知能力核实与实测结果

**能力核实结论**：本机未发现 WorkBuddy 原生的「事件驱动手机/桌面即时推送 API」，也没有可调用的无事件静默或通知去重接口。`automation_update` 只提供一次性/周期任务的创建与查询，任务以「运行结束时产生结果输出」的方式形成通知。因此：

- 提醒的**产生**由 `intraday.py` 事件状态机决定（去重、静默、升级、反转、故障、恢复）；
- 提醒的**送达**由 WorkBuddy 定时任务在任务结束时输出，`--notify-drain --notify-ack` 消费队列；
- **真实延迟取决于定时任务周期，不保证秒级或即时**；
- 不声称已实现即时推送，也不声称手机端送达已从 API 侧验证。

**调度能力实测**：`automation_update` 的 RRULE 校验不接受逗号分隔的多个 `BYHOUR`（尝试 `FREQ=WEEKLY;BYDAY=...;BYHOUR=9,10,11,13,14,15` 时返回 `BYHOUR must be an integer between 0 and 23`）。因此按平台实际能力调整为：

| 任务 | ID / 规则 | 实际频率 | 延迟上限 |
| --- | --- | --- | --- |
| 国家队ETF盘中提醒消费（交易日每小时） | `2257f962-0411-4a68-b0df-f7a5cf9ab546`；`FREQ=HOURLY;INTERVAL=1;BYDAY=MO,TU,WE,TH,FR,SA` | 工作日 + 周六每小时一次；非交易时段只输出一行「跳过」并结束，不执行命令 | 交易时段内约 1 小时 |

任务 `cwd` 为 `D:/work_code2/gjd_research`。无事件静默与去重**不是平台原生能力**：由 `intraday.py` 事件状态机（`silent_when_unchanged`、去重键 `[business_date, family]`）实现；`count=0` 时任务只输出一行状态，但仍会形成一次「任务完成」通知，这是平台限制，无法做到完全静默。

## 11. 事后回放与周报

- `--replay` 读归档 `snapshots.jsonl`，事件与提醒都标 `replayed=true`，不进入「正在发生」的判断。
- 周报按最近 7 天统计采集轮数、时段/时效分布、行情延迟 p50/p90/p95、故障与恢复次数、提醒条数、重复 id、队列积压，并列出「未解释事件」人工复核清单。
