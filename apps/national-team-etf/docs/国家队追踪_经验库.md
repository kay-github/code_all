# 国家队追踪经验库 v2.1 · 2026-11-14

规则以[项目README](../README.md)和`config/rules.json`为准。本文按证据状态维护，旧结论的撤回同样属于研究记录。

## 已复现的数据与算术

1. 缺前值不等于零流量，多日缺口不能塞到某一天；份额合并需统一比较单位；累计舍入误差有共享端点。对应单元测试和归档回归样本。
2. 11月13日254只同源日线复核中，94只最新行换手率被修订，价格、成交量和成交额未变。该次样本支持最新日分母可能滞后，不证明所有基金或每个交易日都遵循同一更新时间。
3. 核心15只当日反推为−24.9亿元，次日反推为−123.7亿元；正式份额估算为−103.4亿元、5日为−320.1亿元。正式数据与反推必须对账，不能把反推舍入范围当作全部风险范围。
4. 上交所默认份额接口只返回近期约10个交易日，必须逐次累积。深交所当前接口明确以次日早间更新为准，业务日期不可套用旧第三方平台的一日偏移。

以上观察详见`gjd_audit_20261114/正式ETF份额复核_20261113.md`、原始不可覆盖批次及来源URL。

## 当前可采用的工作规则

- 对小额变化保留线索，以累计方向、规模占比、持续性和回撤判断升级；正式份额风险与历史反推风险分别计算。
- 事件保留起点和最高等级；短暂回补不清零。连续5天的5日及10日累计均稳健转正后可解除；缺数据不解除。
- 跨产品、跨管理人、跨家族一致性提高核查优先级；这些条件相关，不能当作多份独立身份确认证据。
- 身份和行为分离：未知不代表没有行动，核心载体也不代表国家队；已持有不代表今天买卖。
- 仅完成部分正式份额、目录分页不全、仍为当晚初值或本次采集失败时，保留旧线上版本并记录失败。

## 保留为研究假设，尚未升级为身份事实

此前通过第三方汇总的10只核心ETF匿名持有人结构，得到“2026H1份额减少主要记在机构类别”等结果，保留在原研究文件中。其类别定义、报告日期、份额口径及原始基金报告尚需逐份复核。内部持有人可能与机构/个人口径重叠，不能简单当成互斥分类。

即使该结构拆解成立，也仅描述两个披露时点的净变化，不能排除期间不同资金的相反交易；不能排除散户参与，不能确定科创50下跌由散户止损造成，更不能识别11月13日国家队交易。相关历史月度节奏只描述全体持有人的ETF申赎，不称为国家队出货收益。

0.5%/1%/2%研究阈值、固定减仓先后顺序、按机构占比选择重点通道，均需保留反例、样本外检验与误报/漏报统计，不宣称最优或精准概率。

## 已撤回的结论

- “−123.7亿元是已确认部分/实际流出的下限”：正式份额估算−103.4亿元已构成反例。
- “反推份额近乎不变即可确认当日流量被抹平”：也可能当天确实变化很小，只能触发核查。
- “次日换手率一定已稳定为精确登记份额”：供应商定义和修订不能由采集时间替代核验。
- “匿名结构排除了散户”“科创50下跌确定是散户止损”“机构撤退等于国家队派发”：证据不足。
- v1的成本以下不卖、上涨才派发、只盯一只没有死角、固定金额以下忽略、复权系数修成交量、混合区间实现收益，继续撤回。
- **E20 已推翻（2026-11-15）**：“与其依赖登录时启动的常驻进程，不如让系统每分钟唤醒 `--scheduled`”——技术上能自愈，但 `schtasks` 每分钟拉起 cmd 控制台窗口抢焦点，持续打断用户工作；用户明确要求改用 WorkBuddy 平台定时任务。原条目保留在 §v2.2 表格作演进记录，**不再是现行建议**。
- **E27 部分改写（2026-11-15）**：“盘中 60 秒采集”本机部分已停用，60 秒实时改由页面浏览器端 JSONP 提供；“不复用日频全量链、不每分钟 Git 提交”仍成立。

后续重点补充：交易所全量ETF目录与供应商目录交叉核对、新上市和不明家族核验、实名持有人资料复核、预警误报/漏报及延迟统计。当前目录分页完成不等于全市场覆盖。

## v2.2 盘中 / 调度层工程经验（2026-11-14）

以下都是**工程与平台能力**记录，不是资金行为结论；同样遵循「可推翻、带证据、写失效条件」。

| 编号 | 经验 | 证据 | 置信度 | 失效条件 |
| --- | --- | --- | --- | --- |
| E19 | 本机 `schtasks /Create /SC ONLOGON` 返回「拒绝访问」，`MINUTE` / `DAILY` / `WEEKLY` 均可创建 | 4 组探测：Probe1/2/4 rc=0，Probe3(ONLOGON) rc=1 | 高 | 以管理员身份运行、组策略或 UAC 配置变化 |
| E20 | 与其依赖登录时启动的常驻进程，不如让系统每分钟唤醒 `--scheduled`、由脚本按交易时段自行节流 **【2026-11-15 已推翻，见「已撤回的结论」】** | 14:08:02 真实采集、14:09:01 唤醒被节流跳过；`windows_task.log` / `run.log` 留痕 | 已撤回 | 用户反馈 cmd 窗口持续打断工作，改用平台调度 |
| E21 | WorkBuddy automation 的 RRULE 不接受逗号分隔的多个 `BYHOUR` | `FREQ=WEEKLY;...;BYHOUR=9,10,11,13,14,15` 返回 `BYHOUR must be an integer between 0 and 23`；改 `HOURLY;INTERVAL=1` 成功 | 高 | 平台升级支持多值 BYHOUR |
| E22 | 平台不提供通知送达回执：list/view 只有配置，没有运行记录、执行日志或推送状态 | 一次性实测任务到点后 list 仍只返回 ACTIVE 与配置 | 高 | 平台增加运行历史/送达 API |
| E23 | 「推送成功」不等于「线上生效」；必须独立查页面/JSON/CSV 构建号 | 三次白名单 push 后，线上仍短暂显示上一构建；CI 完成后四项才一致 | 高 | 改为同步部署 |
| E24 | `publish.py` 清空 Git 代理会推送失败 | `Recv failure: Connection was reset`；全局 git 配 7897（实测不通），会话 `HTTPS_PROXY=7890`（实测可用） | 高 | 代理端口或网络策略变化；已改为优先用会话代理 |
| E25 | 断网时故障事件键是 `unknown|data_fault`，恢复后业务日变成实际日期，按新键找不到原故障 → recover 提醒丢失 | 新增 `test_fault_recovers_once_then_is_silent` 复现；修复为在 state 里记 `fault_key` | 高 | 若改为全局固定故障键则不再需要 |
| E26 | 休市时逐只明细是上一交易日残留快照，必须显式标 `signals_realtime=false`，否则会被误读成当日线索 | 周六 `--once` 得到 `business_date=11-13`、`level=L0` 但 `sync.active_count=5` | 中高 | 页面改为完全不渲染休市明细 |
| E27 | 盘中 60 秒采集不能复用日频全量构建链，也不能每分钟 Git 提交 | 页面实时行情走浏览器 JSONP；正式发布只同步一份低频摘要 | 高 | 引入可写的实时后端 |
| E28 | Node VM 精简 DOM 会走「实时通道未启用」静态降级后 `return`，DOM 测试全绿但真实浏览器每轮抛 `ReferenceError: pill is not defined`；DOM 脚本测试**不能替代**真实浏览器 console 抽查 | 负向验证：新增 `renderLive()` 用例在旧页面精确复现 `unhandledRejection: pill is not defined`；补齐 fetch/setInterval/createElement/head 后才真正执行 `render()` | 高 | 页面移除静态降级分支，或 DOM 测试改为真实浏览器执行 |
| E29 | 内联 `data:` SVG favicon 可消除根 `/favicon.ico` 404，避免 console 噪声掩盖真实脚本错误 | 修复前 Playwright console 同时报 pill 错误与 404；修复后 `errs: []` | 高 | 站点改在根路径提供实体图标 |
| E30 | 用户抱怨「太频繁 / 一直打断做事」时，瓶颈常不是调度逻辑而是**调度载体**：本机 schtasks 拉起 cmd 控制台窗口抢焦点，频率越高越不可忍受 | 旧架构约 1440 次/天；改平台任务后工作日 3 次/天、周日 0 次，零窗口 | 高 | 平台提供无窗口后台执行且用户接受更高频率 |
| E31 | 平台 automation 的最小合理粒度是「按天指定时点」：`BYHOUR` 多值被拒但 `BYDAY` 多值可用；`HOURLY;INTERVAL=1` 连夜间周末一起触发，反而制造更多会话与通知 | `FREQ=WEEKLY;BYDAY=MO,TU,WE,TH,FR;BYHOUR=14;BYMINUTE=30` 创建成功，`nextRunAt` 落在下周一 14:30（UTC+8） | 高 | 平台支持多值 BYHOUR 或后台静默无通知运行 |
| E32 | 把「只消费通知」的平台任务改成新架构时，必须让它**自己采集**；否则删掉本机采集器后队列永远为空，提醒链路静默失效 | 旧 prompt 只有 `--notify-drain --notify-ack`；新 prompt 先 `--platform-tick` 再 drain | 高 | 另有独立数据源写入同一队列 |
| E33 | 调度架构切换必须归档旧通知队列，否则历史事件会在下个周期被当作「正在发生」的新提醒发出 | 11-13 遗留 10 条 → `notify_pending_archive_20261115.jsonl`，清空后 drain `count=0` | 高 | 队列条目自带过期判定且消费者会过滤 |
| E34 | 降频到每日 1 帧后，5/15/30 分钟窗口与 L2/L3 升级失去证据基础；必须在**代码里**钳制等级并标 `windows_reliable=false`，不能只写文档 | 单测强制 `decide_level=L3`，`cadence=hourly` 仍输出 L1；realtime 输出 L3 | 高 | 恢复连续分钟采样 |

**待证伪 / 待补**：交易日历只有周末 + 手工 holidays（法定节假日可能误判）；折溢价与 IOPV 未独立核验；无可靠逐笔/主动成交方向；手机端通知送达未取得凭证；盘中基线需累计 5 个完整交易日才能解除冷启动；平台任务实际执行与手机/桌面送达仍无 API 回执，需用户目视确认。
